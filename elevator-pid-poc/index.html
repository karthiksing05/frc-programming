The Elevator Subsystem

An elevator is a linear extension mechanism — it moves a carriage up and down along a fixed rail. In code, we model it as a WPILib SubsystemBase with a TalonFX motor (Phoenix 6). The periodic() method runs every 20ms, reading the encoder and sending voltage commands.

│   SETPOINT   │──→  PIDController  ──┐
│  (meters)    │                      ├──→ VoltageOut ──→ TalonFX ──→ Elevator
└──────────────┘  ElevatorFeedforward ─┘                               │
                        ↑                                              │
                        └──── m_motor.getPosition() (rotations→m) ◄────┘

sticky_note_2 Note

The code uses Phoenix 6 API: TalonFX for the motor, VoltageOut for the control request, and getPosition() for the integrated encoder. WPILib provides PIDController and ElevatorFeedforward for the control math.

Understanding PIDController

sticky_note_2 Note

WPILib's PIDController takes three gains: kP, kI, kD. Each addresses a different aspect of error correction. The controller's calculate(measurement, setpoint) method returns a voltage output.

P — Proportional

Output proportional to the current error (setpoint − measurement). Higher kP → faster response, but too high causes oscillation.

pidVoltsP = kP × error

I — Integral

Accumulates past error over time. Helps eliminate steady-state error (e.g., gravity pulling the elevator down). Be careful — too much causes integral windup.

pidVoltsI = kI × Σ(error × dt)

D — Derivative

Reacts to the rate of change of error. Acts as a damper to reduce overshoot and oscillation.

pidVoltsD = kD × (Δerror / dt)

Feedforward — ElevatorFeedforward

WPILib's ElevatorFeedforward takes three gains:

  • kS — Overcomes static friction (small constant voltage to get the motor moving)
  • kG — Gravity compensation — the key gain for elevators! A constant voltage that counteracts gravity so the PID doesn't have to.
  • kV — Velocity feedforward (V·s/m). Less critical for position holding.
ffVolts = kS·sgn(v) + kG + kV·v

Without kG, the PID controller has to "waste" integral effort just to hold the elevator in place.

warning Warning

On a real robot, PID output is in volts (clamped to ±12V by MathUtil.clamp). Start with small kP values and increase gradually! The simulation here is safe to experiment with.

expand_more Tuning Hints (try yourself first!)
  • Start with only kP (set others to 0). Try kP = 24.0 (remember, PID outputs volts now!)
  • If it oscillates, add some kD (try 6.0)
  • If it sags below the target, set kG (try 4.0V — this fights gravity!)
  • If there's still a small steady-state error, add a tiny kI (try 1.0)
  • A good solution: kP=30.0, kI=1.2, kD=10.0, kG=4.2

science Example

In the 2023 FRC game (Charged Up), teams used elevators to place cones and cubes on a grid. PID control ensured the elevator hit exact heights for low, mid, and high placements — just like the setpoints in this exercise!

Going Further

Once you can hit all four setpoints smoothly with minimal overshoot:

  • Try making the elevator respond faster without increasing overshoot
  • What happens if you set kI very high? (integral windup!)
  • What happens with kG = 0? Watch the steady-state error — the PID has to compensate for gravity alone
  • Can you make it critically damped (no overshoot at all)?
  • Notice how SmartDashboard.putNumber() calls log telemetry — on a real robot, you'd see these in Elastic/Shuffleboard!
